- **close_season index-safety — SAFE.** New body archives ALL active (`update … where status='active'`, 0014:89) BEFORE the single active insert (0014:94-105). Unique indexes are checked per-row at statement time (not deferrable), so the insert never sees a second active. Legacy >1-active can't strand older rows anymore.

So `tournament.prizes` (the materialized amounts the UI/chop-split read) is left byte-identical for every pre-existing scheduled/live/completed fecha. Completed-fecha money is not rewritten by this migration. Confirmed no `perform set_prizes` anywhere in the migration body outside function definitions.

## Findings

- Optional (migration-abort hardening): `0015_fecha_prizes_bust_standalone.sql:74` — the backfill WHERE calls `jsonb_array_length(s.payout_template) > 0`. `payout_template` is `jsonb not null` but the column does NOT enforce array-ness, and `update_season` (0010:128) sets it via `coalesce(p_payload->'payout_template', …)` with no type check — so a non-array value (object/scalar) is *reachable* via that RPC or a direct service_role write. `jsonb_array_length` (and `jsonb_array_elements_text` at 0015:68) **throw 22023 on a non-array**, and because Postgres does not guarantee AND-predicate evaluation order, a single malformed `season.payout_template` row would abort the ENTIRE 0015 migration transaction on prod. Probability is low (schema default is an array; FE sends arrays), so this is Optional not Critical — but the cost of an abort is high and the guard is cheap. Fix: gate with a type-safe expression, e.g. `and jsonb_typeof(s.payout_template) = 'array' and case when jsonb_typeof(s.payout_template)='array' then jsonb_array_length(s.payout_template) else 0 end > 0` (or wrap the whole condition in a CASE). Same latent throw exists at runtime in `create_tournament` (0015:116, `coalesce(jsonb_array_length(v_template),0)` — coalesce can't catch the throw) — worth the same guard.

- Optional (history fidelity, latent): `0015_fecha_prizes_bust_standalone.sql:62-74` — the backfill snapshots the CURRENT `season.payout_template` into every fecha, including already-completed ones. If an admin edited the season template between a fecha completing and this migration, the backfilled `payout_distribution` no longer matches the template that produced that fecha's frozen `prizes`; a future `set_prizes` re-run on that completed fecha would then rewrite its amounts to the newer split. This does NOT rewrite anything now (no auto path re-runs `set_prizes` on a completed fecha — materialize points are open_tournament / confirm_payment / add_rebuy only, 0013), and it is not a regression (Phase-1 `set_prizes` also read the live season template), so impact is latent. Consider: (a) a one-line comment that completed-fecha prizes must never be re-materialized, or (b) if true historical fidelity is wanted, seed completed fechas from the split implied by their frozen `prizes` rather than the current template.

- Optional (close_season tiebreak drift): `0014_season_integrity.sql:79` — `close_season` picks the config-carry-forward season (`v_old`) with `order by year desc limit 1` (NO secondary tiebreak), whereas the repair at 0014:40 uses `(year desc, created_at desc, id desc)`. If two active rows ever shared a year, the two paths could keep/carry different rows. This is MOOT once the single-active index exists (only one active row can exist when close_season runs), so it is defensive only — but aligning `close_season`'s ORDER BY to the repair's full tiebreak removes the discrepancy for free and documents intent.

- FYI: `0015_fecha_prizes_bust_standalone.sql:226` — `set_prizes` reads distribution pcts `order by (e->>'place')::int` but then re-numbers output positions `1..k` sequentially (0015:278-285), ignoring the actual `place` values except for ordering. Harmless for the backfill (always contiguous 1..len) and for the default template, but a per-fecha distribution with GAPS (e.g. places [1,3,5] after an admin removes a row in the step-5 editor) collapses to positions [1,2,3]. This is a step-5 FE / contract concern, not a migration-data concern — flagging so the editor pass (correctness lens) confirms places stay contiguous or that renumbering is intended.

- FYI: `0015_fecha_prizes_bust_standalone.sql:373-411` — `eliminate_multi` validates each entry id is in-play but does NOT dedupe `p_entry_ids`. A duplicated id in the tie branch produces two `with ordinality` rows for one entry (0015:408-410), making the `update … from` match nondeterministic and skewing `v_alive_incl - v_n` lone-survivor detection (0015:414). Not a stored-data-migration issue; belongs to the adversarial/correctness lens — noted for cross-reference.

- FYI: `create_tournament` (scaled subset) and the backfill (full template) seed DIFFERENT distributions for the same season, so two SCHEDULED fechas can carry different place-counts depending on whether they pre- or post-date 0015. For the default 3-element template both resolve to 3 places (scaling floor is 3), so no visible effect today; only matters for longer templates. Admin can edit either; not a defect.

- FYI: No down/rollback migrations exist, but the project is reset-based (`supabase db reset`) and every 0014/0015 change is additive (one index, two nullable/defaulted columns, function replacements) with an idempotent, `is null`-guarded backfill — no destructive DROP, no data loss on re-apply. Acceptable for this model; noted only for completeness.
